## 0. Goal

Issue #83 asks whether the simulated student environment is valid enough for the benchmark to mean anything.

The acceptance question is:

> Given a persona contract, can the simulator produce student behavior that a human evaluator recognizes as that assigned persona across tasks, turns, and tutor behavior variation?

This is environment validation, not tutor scoring. In the NBA analogy from the issue:

- External agent / tutor = player or team.
- Task conversation = game.
- Student simulator + workspace = court, ball, rules, opposing defense, and game environment.
- Tutor rubric = scoring rulebook for tutor performance.
- Judge validation = whether the referee applies the rulebook reliably.
- Student simulator validation = whether the court/opponent/game environment behaves as designed.

Therefore, this work must validate the student simulator before using its conversations to score external tutor agents.

## 1. Non-Negotiable Implementation Constraints

### 1.1 No fallback in final validation data

All fallback paths that can silently convert missing or invalid data into apparently valid metrics must be removed or made hard failures.

Specifically:

- No control-from-D4 fallback.
- No missing control judge outputs accepted as optional for final validation.
- No synthetic student fallback messages.
- No using fixture openings as generated student behavior.
- No treating duplicated or templated judge outputs as valid judged data.
- No reporting abnormal simulator/session termination as normal completion.

If an expected artifact is absent, invalid, duplicated, or generated by a non-judge template path, validation must fail loudly.

### 1.2 Preserve old results by renaming, not modifying

The old result path must not be edited in place.

Current old path:

```text
bench/experiments/student_sim_stability/results/
```

Before new execution, rename it to an archive path such as:

```text
bench/experiments/student_sim_stability/results_legacy_20260423/
```

or, if multiple archives are expected:

```text
bench/experiments/student_sim_stability/archive/results_20260423_pre_issue83/
```

After the rename, all new work should use a fresh result directory:

```text

```

No scripts should read from legacy results unless explicitly asked to compare or audit them.

### 1.3 Work in experiment-private files

Do not modify system-shared source artifacts such as:


## 3. Known Problems in Current Results

### 3.1 D4 contains non-judge template outputs

`bench/experiments/student_sim_stability/doc/todo.md` records:

- 50 out of 234 D4 judge outputs are hardcoded/template score payloads.
- These cover 10 duplicate score signatures.
- They affect tasks `S03_mean_reversion_research` and `X02_lookahead`.
- They can inflate D4 and reduce apparent variance.

Issue #83 final validation must treat this as a hard failure.

### 3.2 Control section uses the wrong metric

Existing `judge_inputs/control__*.json` count is 0.

Existing `judge_outputs/control__*.json` count is 0.

The aggregate control rows are currently produced by fallback logic in `pipeline/aggregate.py`, which converts D4 control `per_turn_fidelity` into `distinctiveness`.

That is invalid because it measures whether generic control messages resemble a persona, not whether persona and generic conversations are distinguishable.

Issue #83 final validation must require real `_DISTINGUISH_PROMPT` control judge outputs.

### 3.3 Fixed openings contaminate student metrics

`runner.py` starts every conversation with task fixture text:

```python
opening = (task.student_openings or {}).get(
    persona_id, "Hi, I need help with this topic."
)
conversation: list[dict] = [{"role": "user", "content": opening}]
```

`pipeline/render_judge_prompts.py` then treats every `role=user` turn as a student message.

This means D1/D2/D3/D4 can count persona-specific fixture text as if it were generated by the student model.

Issue #83 final validation must exclude fixture openings from generated-student metrics or mark them as fixture turns.

### 3.4 Control conversations use persona-specific openings

Control uses a generic student description, but still uses the persona-specific `student_openings[persona_id]`.

This contaminates persona-vs-generic comparison.

Issue #83 final validation must use neutral control openings.

### 3.5 Report is chart-first, not rubric-first

Current `report.py` mostly shows charts and short explanations. It does not consistently provide:

1. rubric definition;
2. judge context and prompt inputs;
3. score fields and scale;
4. aggregation formula;
5. chart;
6. insight guide and action recommendations.

Issue #83 requires every report section to follow that order.

### 3.6 Persona contract is implicit

Persona behavior currently lives across:

- `bench/personas/*.json`
- `server/config/prompt_config.py`
- `evaluator.py` prompt templates
- task-specific openings

There is no stable first-class persona contract artifact for the experiment.

Issue #83 requires first-class persona contracts.

### 3.7 No controlled probe suite

Current experiment jumps directly to live tutor robustness.

Issue #83 requires:

- single-turn targeted probes;
- scripted multi-turn tutor conversations;
- blind distinguishability prompts;
- live tutor robustness only after probes pass.

### 3.8 No human quant expert alignment

There is no human calibration sample, no human labels, no agreement metric, and no disagreement examples.

Issue #83 requires an artifact path and report status for human alignment.

### 3.9 No multi-judge agreement status

Current pipeline uses one judge model per prompt.

Issue #83 requires multi-judge status, and ideally optional agreement logic.

### 3.10 No model comparison policy

Current report directly ranks `gpt-5.4`, `claude-sonnet-4-6`, and `gemini-3.1-pro-preview`.

Issue #83 requires a policy that labels comparisons as same-level or cross-vendor candidate selection, with parameter/context/price/tier metadata where available.

### 3.11 Failure taxonomy is incomplete

D4 already asks for `knowledge_leak` and `co_teacher_drift`, and existing aggregate data contains nonzero values for those fields. But report does not aggregate or explain them.

Issue #83 requires failure types:

- knowledge leak;
- under-competence;
- emotional mismatch;
- generic-student behavior;
- co-teacher drift;
- task-forgetting;
- contradiction with persona contract.
