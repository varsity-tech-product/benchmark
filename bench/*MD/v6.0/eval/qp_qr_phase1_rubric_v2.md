# QP/QR Phase 1 Rubric v2

> **创建日期**: 2026-04-21
> **状态**: 待人工审核（human calibration 前置版本）
> **量纲**: 所有 LLM judge 子维度统一为 INTEGER 1-5
> **格式**: 参照 6D rubric 渐进式结构（ceiling check → baseline check → upward check）
> **设计原则**: 每条标准描述可在 trace/对话文本中直接观察到的行为，不使用抽象质量判断

---

## 设计说明

### 什么是"可观察的标准"

**不合格（抽象判断）**：
- "输出是有效的"
- "执行过程是合理的"
- "代码质量良好"

**合格（可观察事实）**：
- "所有 shell_exec 调用的结果中，最终状态均标记为 [OK]"
- "在第一个工具调用之前，agent 对话文本中出现了对任务步骤的列举"
- "没有任何工具以完全相同的参数被调用超过一次（错误重试除外）"

### Human Calibration 说明

人类评分员使用本文档时，应：
1. 打开 agent 的完整 trace（工具调用序列 + 对话文本）
2. 对每个子维度，从 **Ceiling Check** 开始逐步向上判断
3. 每条标准均以"是/否"回答，不依赖主观感受
4. 存疑时记录具体的 trace 位置（turn index + 内容片段）以供 calibration 讨论

### 评估流程（与 6D 一致）
```
Step 1. Ceiling Check: 是否存在任意 Score 1 条件？ → 是：得 1 分，停止
Step 2. Baseline Check: Score 3 的所有条件是否全部满足？
        → 否：得 2 分（部分满足）
        → 是：至少 3 分，进入 Upward Check
Step 3. Upward Check: Score 4 条件是否满足 ≥2 项？ → 否：得 3 分
        → 是：至少 4 分。Score 5 条件是否满足 ≥2 项？ → 否：得 4 分 → 是：得 5 分
```

## 一、QR — Quant Result

### 1.1 completeness（完整性）

**评估对象**：agent trace 中的工具调用记录和文件写入记录
**参照来源**：expected_outcome 文本 + reference result 的文件列表

```
Score 1 — Ceiling Check（任意一条 → 得 1 分）:
  (a) expected_outcome 中明确列出的输出类型（如 .csv 文件、回测结果、某类指标）
      在整个工具 trace 中无任何对应的工具调用记录（file_write / shell_exec / 专项工具均无）
  (b) 唯一的"输出"以 agent 对话文字描述形式出现（"我计算了 Sharpe ratio 为 1.23"），
      但工具 trace 中无任何对应的实际执行记录（无 [OK] 的计算步骤）
  (c) expected_outcome 要求的核心数值指标在所有标记为 [OK] 的工具输出文本中均未出现

Score 2 — 至少 2 条:
  (a) expected_outcome 列出 N 类输出，工具 trace 中有对应记录的仅 N-2 类或以下
  (b) 存在文件写入记录（file_write [OK]），但该文件在后续步骤中从未被读取或引用
  (c) expected_outcome 要求图表类输出，但工具 trace 中无任何图表文件的 save 记录

Score 3 — 全部满足（任意一条不满足 → 不得 3 分）:
  (a) expected_outcome 中每一类输出，在工具 trace 中均有至少一条对应的 [OK] 执行记录
  (b) 每项被要求的核心数值指标，其具体数值出现在至少一个 [OK] 工具输出的文本中
  (c) 若 expected_outcome 要求文件产出，workspace 文件列表中可找到对应文件
  (d) 无 Score 1 的任何条件

Score 4 — meets Score 3 + 至少 2 条:
  (a) expected_outcome 中的"次要"或"补充"输出项（若有）也在 trace 中有对应的 [OK] 记录
  (b) agent 产出的指标数量 ≥ reference result 文件中列出的指标数量
  (c) 图表类输出有明确的文件名记录，且文件名体现了图表内容（非 output.png、chart.png 等）

Score 5 — meets Score 4 + 至少 2 条:
  (a) agent 产出了 expected_outcome 未列出的额外分析（在 [OK] trace 中可见），
      且该分析对核心结论有直接的支撑作用（可从 agent 对话文本中确认其引用关系）
  (b) agent 产出的文件数量 ≥ reference result 的文件数量
  (c) 每项数值输出在 agent 对话文本中有明确的结论性解读（不只是打印数字）
```

### 1.2 output_usability（输出可用性）

> **说明**：本维度评估输出格式的可用性，不评估数值的统计正确性。
> 数值准确性由程序化 code_eval 组件（Layer C）处理。

**评估对象**：工具 trace 中的输出文本、[OK]/[FAIL] 标记、文件格式信息

```
Score 1 — Ceiling Check（任意一条 → 得 1 分）:
  (a) 存在标记为 [FAIL] 的关键工具调用，且在整个后续 trace 中未出现对该调用的修复和重新执行
  (b) 某个输出文件在后续读取时产生 FileNotFoundError 或解析错误（可在工具输出文本中观察到）
  (c) 核心数值输出中出现 NaN、inf 或空字符串，且 agent 未识别并处理这些异常值

Score 2 — 至少 2 条:
  (a) DataFrame 类输出的列名为整数索引（0, 1, 2...），而非语义化标签
      （可在工具输出的打印文本中直接观察）
  (b) 时序数据的日期列数据类型为 object/string 而非 datetime
      （可从 dtypes 输出或 index 打印中确认）
  (c) 输出文件成功写入（[OK]），但内容格式在下游读取时需要手动转换才能使用
      （如 JSON 嵌套层级与 expected 不符，可从读取工具的输出中观察）

Score 3 — 全部满足:
  (a) 所有工具调用均以 [OK] 结束，或失败后在后续步骤中被修复并重新执行为 [OK]
  (b) 所有 DataFrame 输出有语义化列名（可在 trace 中打印的表头文本中验证）
  (c) 产出文件在后续步骤中被成功读取（无读取错误出现在 trace 中）
  (d) 无 Score 1 的任何条件

Score 4 — meets Score 3 + 至少 2 条:
  (a) 每个数值结果在 agent 文本中带有明确的标签说明
      （如"Sharpe Ratio: 1.23"而非仅输出"1.23"）
  (b) 时序类 DataFrame 的索引或日期列为 DatetimeIndex
      （可从 `.index` 或 `.dtypes` 的工具输出文本中确认）
  (c) 图表文件存在（workspace 中可见），且文件名体现图表内容（非 plot.png 等）

Score 5 — meets Score 4 + 至少 2 条:
  (a) 数值输出包含自解释的格式，明确说明指标含义、时间范围或对比基准
      （如"策略 Sharpe(2020-2024): 1.23 vs 基准: 0.87"）
  (b) 产出文件命名包含语义信息，使其在文件列表中含义清晰
      （如 sharpe_momentum_2020_2024.csv 而非 result.csv）
  (c) 所有中间步骤的数值与最终输出的数值在逻辑上一致
      （无前后矛盾，可通过比对 trace 中多处出现的同名指标数值来验证）
```

## 二、QP — Quant Process

### 2.1 process_reasonableness — problem_decomposition（问题分解）

**评估对象**：第一个工具调用之前的 agent 对话文本 + 整体工具调用顺序

```
Score 1 — Ceiling Check（任意一条 → 得 1 分）:
  (a) 第一轮 agent 回复中，第一个工具调用出现在任何文字分析之前（对话开头即调用工具，
      无任何对任务的文字说明）
  (b) 工具调用的实际顺序与该类任务的基本依赖顺序相反，导致明显的执行失败
      （如：在数据加载之前调用了需要该数据的计算函数，且出现了相关错误）
  (c) expected_outcome 中明确列出的某类输出，在整个 trace 中无任何对应的工具调用步骤
      （非失败，而是完全没有尝试）

Score 2 — 至少 2 条:
  (a) agent 文本中有规划描述，但实际工具调用顺序与描述中的步骤顺序不一致
      （可对照文本描述和 trace 中工具调用的时序来验证）
  (b) 在执行过程中（非开头），agent 文本中出现"我需要先去…"或等效的补充前置步骤
      （说明该依赖未被提前识别）
  (c) 相邻工具调用之间缺少文字衔接，每个工具调用独立出现无前后承接的文字说明

Score 3 — 全部满足:
  (a) 在第一个工具调用之前，agent 对话文本中出现了对任务将如何执行的描述
      （至少包含 2 个可识别的步骤意图，哪怕是一句话带过）
  (b) 所有数据获取类工具调用（fetch_market_data 等）出现在依赖该数据的计算工具调用之前
      （可按 trace 顺序逐条确认）
  (c) 无 Score 1 的任何条件

Score 4 — meets Score 3 + 至少 2 条:
  (a) 分解描述以结构化列表形式出现（含步骤编号或 bullet points），而非流水式文字
  (b) 分解中明确提到了数据来源、时间窗口或关键参数（即具体到要用什么数据做什么）
  (c) 整个 trace 的工具调用顺序与开头分解描述的步骤顺序逐一对应

Score 5 — meets Score 4 + 至少 2 条:
  (a) 分解中提到了潜在的困难点或条件判断（如"若数据不足 N 天则..."）
  (b) agent 明确说明了各步骤之间的数据传递关系（"步骤 2 使用步骤 1 的输出作为输入"）
  (c) 分解的粒度与 category-specific 最优执行路径的步骤数量相当
      （参照任务 category 的标准路径描述验证）
```

### 2.2 process_reasonableness — execution_soundness（执行合理性）

**评估对象**：每个工具调用的参数 + agent 对结果的解读文字

```
Score 1 — Ceiling Check（任意一条 → 得 1 分）:
  (a) 工具调用使用的参数与任务描述中的要求明显矛盾
      （如任务指定计算 2020-2024 年数据，但工具调用中使用了 2010-2015 年的参数）
  (b) agent 对 [OK] 工具输出中的数值进行了与该数值方向相反的解读
      （如输出为正收益，agent 文本描述为"策略亏损"）
  (c) 存在对同一变量先赋值 A、后赋值 B，但后续计算同时引用两个值而无说明的情况
      （导致结果不可信）

Score 2 — 至少 2 条:
  (a) 工具调用使用的参数选择无任何文字依据，且与任务语境明显不匹配
      （如计算移动均线时选择了与任务描述无关的窗口长度）
  (b) agent 对工具输出结果未做任何解读，直接进入下一步（工具调用之间无文字过渡）
  (c) 某项计算使用了在该 trace 中从未被加载或定义的数据
      （可通过检查变量/数据的来源 trace 来验证）

Score 3 — 全部满足:
  (a) 每个工具调用使用的参数与任务描述中的相关要求一致
      （可逐一对照任务描述和工具调用参数列表验证）
  (b) agent 对每项关键工具输出给出了至少一句解读性文字（不只是打印结果）
  (c) 每项计算所依赖的数据在该工具调用之前已经出现在 trace 中（无未定义引用）
  (d) 无 Score 1 的任何条件

Score 4 — meets Score 3 + 至少 2 条:
  (a) 参数选择有明确的文字说明依据（如"选择 20 日均线因为任务要求短期信号"）
  (b) 对异常或意外的工具输出结果（如极端值、空数据）有识别并在文字中说明处理方式
  (c) 中间计算结果的数量级/方向在文字中被显式核实（如"收益率为正，符合预期"）

Score 5 — meets Score 4 + 至少 2 条:
  (a) agent 主动指出了某个结果中的异常或边界情况并说明了其对结论的影响
  (b) 参数选择与 category 最优实践一致，且 agent 文字中提到了选择理由
  (c) 每个关键的中间结果都被显式地传递给下一步（文字中明确引用前一步的输出数值）
```

### 2.3 process_reasonableness — error_handling（错误处理）

> **重要说明**：
> - **有错误场景**（trace 中出现 [FAIL]）：按下方标准评估
> - **无错误场景**（trace 中无任何 [FAIL]）：Score 3 为上限；Score 4 需有主动防御性代码写法的证据

```
[有错误场景]

Score 1 — Ceiling Check（任意一条 → 得 1 分）:
  (a) 同一工具调用（相同函数名 + 相同参数）在 [FAIL] 后未做任何修改直接重复调用
  (b) 修复代码针对的是错误信息中的症状表现，而非错误根因
      （可对照：NameError 的修复是否真正定义了该变量，而非用 try/except 跳过）
  (c) 出现 [FAIL] 后 agent 对话文本跳过该错误继续后续步骤，从未尝试修复

Score 2 — 至少 2 条:
  (a) 修复后代码的改动与 [FAIL] 信息中描述的错误类型不对应
      （如 KeyError 的修复改动了与 key 无关的部分）
  (b) 同一错误类型（如 ImportError）在不同步骤中重复出现超过 1 次
  (c) 修复后未重新执行验证，直接继续后续步骤

Score 3 — 全部满足:
  (a) 每次 [FAIL] 之后，下一个同类工具调用改动了与错误信息直接相关的参数或代码部分
      （可对照：TypeError → 改动了类型转换；NameError → 补充了变量定义）
  (b) 同一错误在修复后不再重复出现（[FAIL] 标记不再出现相同的错误信息）
  (c) 无 Score 1 的任何条件

Score 4 — meets Score 3 + 至少 2 条:
  (a) 修复后有明确的重新执行步骤，且该步骤结果为 [OK]
  (b) agent 文字中解释了错误产生的原因（而非仅展示修复后代码）
  (c) 修复后的代码相比原版增加了防止同类错误的处理逻辑
      （如增加了 `.get()` 替代直接 key 访问，或增加了 `if df is not None` 判断）

Score 5 — meets Score 4 + 至少 2 条:
  (a) 从 [FAIL] 到 [OK] 只经历了 1 次修复尝试（无多次试错）
  (b) 错误修复同时改进了相关代码的其他部分（而非最小化修复）
  (c) agent 从当前错误中提炼出对后续步骤的改进（如"这个错误说明数据中有空值，
      我在后续步骤中将加入非空检查"，可在文字中观察到）

[无错误场景，Score 3 为上限]

Score 3: trace 中无任何 [FAIL]，且无明显的裸写法
  （如未被 try/except 保护的文件读取、未检查长度的列表访问等）

Score 4（无错误场景）— meets Score 3 + 至少 2 条:
  (a) 对可能失败的操作有明确的前置检查
      （如文件读取前有 os.path.exists() 检查；可在代码文本中直接观察）
  (b) 对可能包含空值的数据有 .dropna() 或 .fillna() 等处理，且在执行步骤之前出现
  (c) 对数值计算有合理性校验（如检查分母不为零，或打印中间值确认数量级正常）
```

### 2.4 step_efficiency — redundancy_avoidance（冗余避免）

**评估对象**：工具调用的名称 + 参数列表（跨整个 trace 对比）

```
Score 1 — Ceiling Check（任意一条 → 得 1 分）:
  (a) 同一工具以完全相同的参数被调用 ≥3 次，且调用之间无任何 [FAIL] 记录
      （纯重复，非错误重试）
  (b) 某次数据获取调用的结果（dataset）在后续所有工具调用中均未出现引用
      （获取了但完全没有使用）
  (c) 在 agent 文字中出现"已完成任务"或等效的结论之后，trace 中仍出现新的工具调用
      （任务结束后继续调用）

Score 2 — 至少 2 条:
  (a) 同一工具以完全相同的参数被调用 2 次，且调用之间无 [FAIL] 记录
  (b) 某次获取的数据仅被引用了 1 次，而后续有多处本可复用该数据但重新获取
  (c) 存在连续的多个工具调用计算了同一个指标（如两次计算同一个 moving average，
      参数相同，中间无对第一次结果的否定）

Score 3 — 全部满足:
  (a) 不存在参数完全相同的重复工具调用（错误重试除外：[FAIL] 后的相同调用不计）
  (b) 每个数据获取工具调用的结果在后续步骤中至少被引用一次
      （引用可以是直接使用该变量，或在文字中提到该数据的结果）
  (c) 无 Score 1 的任何条件

Score 4 — meets Score 3 + 至少 2 条:
  (a) 存在明确的变量复用：前置步骤获取的结果被多个后续步骤引用，而非每次独立获取
  (b) 相似的操作被合并到一个工具调用中完成（如一次获取多个指标，而非分多次）
  (c) agent 文字中出现"使用上面已计算的…"或等效的复用说明

Score 5 — meets Score 4 + 至少 2 条:
  (a) 整个 trace 中工具调用总数与参考 trace 的工具调用总数之差 ≤2
      （说明 agent 找到了接近最简的执行路径）
  (b) agent 在规划阶段就提到了会复用某个中间结果（预先规划了复用，而非事后发现）
  (c) 无任何可合并但未合并的相邻同类调用
```

### 2.5 step_efficiency — logical_sequencing（逻辑顺序）

**评估对象**：工具调用的时序顺序（trace 中的调用先后关系）

```
Score 1 — Ceiling Check（任意一条 → 得 1 分）:
  (a) 图表/可视化工具调用出现在被可视化数据的获取调用之前
      （可按 trace 顺序确认：plot 类调用在对应 fetch 类调用之前）
  (b) 指标计算工具调用出现在所需原始数据加载之前，且产生了相关错误
  (c) 因顺序错误导致 ≥3 个步骤需要重新执行（可从 trace 中计数有多少次"重来"）

Score 2 — 至少 2 条:
  (a) 存在 1 处顺序倒置（依赖未就绪时执行了依赖它的步骤），导致至少 1 次重新执行
  (b) 某个中间结果被计算后，其前置数据才在后续步骤中被检查/修正
      （先用后检，顺序不当）
  (c) 相互强依赖的步骤之间被不相关的步骤打断，造成逻辑混乱
      （可从 trace 结构中观察到明显的跳跃）

Score 3 — 全部满足:
  (a) 所有可视化/图表类工具调用出现在其所需数据获取完成之后
  (b) 所有指标计算调用出现在原始数据加载完成之后
  (c) trace 中无任何因顺序错误导致的回退重做步骤
  (d) 无 Score 1 的任何条件

Score 4 — meets Score 3 + 至少 2 条:
  (a) 相互依赖的步骤在 trace 中连续出现（无不相关步骤插入其间）
  (b) 数据加载后立即出现数据质量检查（如 .info()、.describe() 或空值检查），
      在计算步骤之前
  (c) 分析结论类工具调用（如统计汇总）出现在所有数据处理完成之后

Score 5 — meets Score 4 + 至少 2 条:
  (a) trace 的工具调用顺序与 category-specific 最优路径描述的步骤顺序逐一对应
  (b) 后置步骤所需的数据在前置步骤中已经准备好（无"刚好差一步"的情况）
  (c) 整个 trace 读起来呈现清晰的阶段分割：获取 → 处理 → 分析 → 输出，
      各阶段不回退（可从工具类型的变化来验证）
```

### 2.6 code_process — debugging_competence（调试能力）

> **说明**：无代码错误场景（trace 中无 [FAIL] 代码执行）时，Score 3 为上限。

```
[有代码错误场景]

Score 1 — Ceiling Check（任意一条 → 得 1 分）:
  (a) 在 [FAIL] 执行结果之后，下一次代码执行内容与失败代码完全相同
      （零修改直接重试）
  (b) 修复代码的改动部分与 [FAIL] 报错信息中的错误类型不对应
      （如 NameError: 'df' is not defined，但修复改动了与 df 无关的代码部分）
  (c) 修复方式是注释掉报错行或添加 try/except pass 以绕过错误，而非解决根因

Score 2 — 至少 2 条:
  (a) 针对同一 [FAIL] 尝试了 ≥2 次修复，且前两次修复改动的方向不一致
      （说明未定位到根因，在试错）
  (b) 修复后代码执行成功 [OK]，但输出结果为空或 NaN，agent 未察觉并继续
  (c) 同一类型的错误（如同一 column KeyError）在后续不同步骤中再次出现

Score 3 — 全部满足:
  (a) 每次 [FAIL] 之后，修复代码的改动部分与报错信息描述的错误直接对应
      （NameError → 补充变量定义；TypeError → 修改类型转换；KeyError → 修正 key 名称）
  (b) 修复后执行结果为 [OK]，且输出数值不为空/NaN（在 trace 中可确认）
  (c) 相同类型的错误在整个 trace 中不再重复出现
  (d) 无 Score 1 的任何条件

Score 4 — meets Score 3 + 至少 2 条:
  (a) 修复后有明确的输出验证（print 或 assert，可在 [OK] 结果文本中确认）
  (b) agent 在文字中解释了报错原因（而非静默地修改代码）
  (c) 修复后的代码包含防止同类错误的额外检查
      （如在 KeyError 修复后增加了 .get() 或 key in dict 的判断）

Score 5 — meets Score 4 + 至少 2 条:
  (a) 从 [FAIL] 到最终 [OK] 只经历了 1 次代码修改（一次命中根因）
  (b) 修复范围最小（只改动了导致错误的代码，其他代码未变动）
  (c) agent 将当前错误的经验应用于后续步骤
      （文字中可见"为避免类似问题，后续步骤我将..."的表述）

[无代码错误场景，Score 3 为上限]

Score 3: 代码执行全部 [OK]，且无明显的不安全写法（如裸文件访问、未检查空值的直接运算）

Score 4（无错误场景）— meets Score 3 + 至少 2 条:
  (a) 对文件读取类操作有前置存在性检查（os.path.exists 或 try/except FileNotFoundError，
      可在代码文本中直接查找）
  (b) 对可能含空值的列有显式的 .dropna()、.fillna() 或 isna() 检查，
      且出现在依赖该列的计算之前
  (c) 分母类变量在被除之前有不为零的检查（可在代码文本中查找 != 0 或 > 0 的判断）
```

### 2.7 code_process — incremental_development（渐进式开发）

**评估对象**：file_write（或等效的代码写入工具）与 shell_exec（或等效的执行工具）的交替模式

```
Score 1 — Ceiling Check（任意一条 → 得 1 分）:
  (a) 在整个 trace 中，从首次代码写入到首次代码执行之间，代码写入量超过 80 行
      且期间无任何中间执行（一次性写完再执行）
  (b) 发现错误后，需要修改 ≥3 个此前已完成的独立代码块（说明错误影响面极广，
      来自于缺乏中间验证）
  (c) 在所有主要功能代码完成后才进行第一次测试性执行

Score 2 — 至少 2 条:
  (a) 连续出现 ≥3 次代码写入之后才出现 1 次执行（写多执少的模式）
  (b) 某个核心功能模块（如数据处理函数或策略逻辑）写入后未经执行就被后续代码依赖
  (c) 发现错误后需要修改 2 个此前已完成的代码块

Score 3 — 全部满足:
  (a) 在整个 trace 中，代码写入和执行的交替频率满足：每次超过 20 行的代码写入
      之后出现至少 1 次执行
  (b) 发现错误时，修改范围限于当前正在开发的代码块（已完成并通过执行的代码无需修改）
  (c) 无 Score 1 的任何条件

Score 4 — meets Score 3 + 至少 2 条:
  (a) 每个逻辑独立的函数或模块写入后均有独立的执行验证
      （可从"写入函数 → 执行该函数 → 写入下一个函数"的 trace 模式确认）
  (b) 中间执行结果在 agent 文字中被明确检视（打印了中间值并确认符合预期）
  (c) 每次执行后，后续代码写入明确基于前次执行结果（如"输出为 1000 行，符合预期，
      继续下一步"，可在文字中观察）

Score 5 — meets Score 4 + 至少 2 条:
  (a) 整个 trace 呈现"写 ≤15 行 → 执行 → 写 ≤15 行 → 执行"的一致节奏
      （可通过统计各次 file_write 的行数变化来验证）
  (b) 每次执行后的输出结果被显式确认（assert 或明确的数值对比），而非仅打印
  (c) 复杂逻辑被拆成多个小步骤分别验证后再组合
      （如先验证数据加载正确，再验证单个指标计算，再验证组合逻辑）
```

## 三、Human Calibration 协议

### 3.1 评分流程

1. **独立打分**：评分员阅读 trace 后，按照每个维度的 Evaluation Process 流程独立打分
2. **记录依据**：对每个非 3 分的打分，记录支撑该分数的具体 trace 位置
   （格式：`Turn N: "[引用的 trace 文本片段]" → 触发 Score X 的条件 Y`）
3. **对齐讨论**：两个评分员分歧 ≥2 分时，进行对齐讨论，以 trace 证据为准
4. **边界案例记录**：将对齐后仍有争议的标准记录到 calibration issue log，
   作为 rubric 迭代的输入

### 3.2 常见歧义处理原则

| 歧义场景 | 处理原则 |
|----------|----------|
| 某条标准"基本满足"但有轻微偏差 | 按 Score 2/4 的部分满足逻辑处理，不向上取整 |
| Score 1 条件存在但影响极微 | Score 1 是一票否决，不因"影响小"而忽略 |
| Trace 文字语义模糊，无法确认 | 按"不可观察"处理，不对应该条 Score 4/5 标准打分 |
| 无错误场景下的调试能力/错误处理 | 严格按照各维度"无错误场景"说明的 Score 3 上限处理 |

### 3.3 Calibration 批次建议

- **第一批**（首次）：选取 10 个任务，覆盖 3 种 category，2 种 persona，含 ≥2 个有 [FAIL] 的任务
- **目标一致性**：同一任务两名评分员的各维度得分之差均 ≤1 分视为通过
- **迭代触发**：若任意维度的评分员间一致性 < 80%，对该维度 rubric 进行修订
